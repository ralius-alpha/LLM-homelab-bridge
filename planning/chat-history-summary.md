## 1. プロジェクトの目的・背景

### きっかけ
自宅の余っているPCにローカルLLM（Ollama等）を構築し、API経由でアクセスできるようにした上で、それを「社内Tips」としてまとめたい、というのが出発点だった。

### 最初の障害：データ送信問題
社内には専用AIチャットが既にあり、ビジネス要件で「社外システムへのデータ送信」が違反になるケースが多い。自宅PCへのデータ送信も本質的には同じ行為であり、「社内Tips」として展開すると、以下のリスクがあると初期のやり取りで指摘された。

- 自宅PCは会社の管理外システムであり、監査ログの対象外
- 「Tipsとして社内展開していた」事実が会社の黙認と解釈されるリスク
- 個人の技術力アピールが「組織のルールや空気を読めない人」という評価につながりかねない

### 個人的な動機（背景として簡潔に）
ユーザーは自身の技術力に自負があり、直近のプロモーション推薦が通らなかったというフィードバックを受けていた。「PJT貢献度より会社貢献が重要」と言われた一方、社内勉強会は内容が浅く時間を割く価値を感じられない、という状況があった。この個人的な閉塞感が、「業務外の個人プロジェクトとして技術発信し、それを会社にも還元する」という方向性を選ぶ動機になっている。

### 方向転換
議論の結果、以下の方針に着地した。

- 業務利用は明確に不可とし、あくまで個人のプライベート活用（「次世代AIエージェントの感覚を先取りする個人実験」）と位置づける
- 「隠して社内だけで完結させる」より、「業務外の個人活動として堂々と外部公開し、その成果を自発的に社内共有する」方が評価上ポジティブに働くという判断（外部公開済みの活動を還元する方が、業務データ流用の疑念を払拭しやすく、継続性・自発性のアピールにもなる）
- その後、社内のAI推進担当者から「投稿頻度の低い社内掲示板を活性化したい」という要望があり、月刊連載（「ディアゴスティーニ方式」）として12ヶ月ロードマップを組む方針に発展した

### さらなる方向転換（03.txtでの見直し）
連載が具体化する過程で、「業務利用不可」の注意書きが公開リポジトリに入っていることの矛盾が指摘された。社外の読者に向けた文書の中に「所属組織とは無関係です」という社内向けの言い訳が混在しており、不自然だという気づきである。最終的に、

- 公開リポジトリ（LLM-homelab）には業務利用不可の文言を一切書かない（社外向けとして自然な、軽い一般的免責のみ）
- 「業務利用不可」「所属組織とは無関係」という社内向けアリバイ文言は、社内Teams・掲示板への投稿本文の冒頭に貼るテンプレートとして bridge 側に移動する
- 公開リポジトリから「社内掲示板」という語自体も削除し、純粋に社外向けリポジトリとしての一貫性を持たせる

という整理に落ち着いた。

## 2. リポジトリ構成と役割

2リポジトリ構成が確定している。

### `LLM-homelab`（公開想定）
連載コンテンツ本体。「眠ってるPCで作る、俺だけのAIエージェント 〜次世代AIの感覚を、毎月1ステップずつ手に入れる12ヶ月の旅〜」という連載タイトルで、GitHub（Public）+ Zenn Book で展開する想定。社内向けの文言・注意書きは一切含まない。

### `LLM-homelab-bridge`（非公開）
戦略・運営メモを管理する完全非公開リポジトリ。「艦橋（Bridge）」というリポジトリ名には二重の意味が込められている。

- **橋渡し（Bridge）**: 個人プロジェクトと社内外の各チャネル（Zenn・社内掲示板・社内関係者）をつなぐ運営情報の中継地点
- **艦橋（司令室）**: プロジェクト全体の戦略司令室。戦略・本音・振り返り・社内政治対応をここで一元管理する

命名は「warroom」「strategy」「private」等の候補も検討されたが、万一画面共有等で見られても「何かの接続ツールね」としか思われない無害さを理由に「bridge」が選ばれた。

ディレクトリは艦船メタファーで統一されている。

| ディレクトリ | 艦内施設 | 役割 |
|---|---|---|
| `planning/` | 作戦室 | 戦略・全体方針（overall-strategy.md, differentiation.md 等） |
| `connections/` | 通信室 | 社内関係者との連携メモ（PLとのコミュニケーション計画等） |
| `crossings/` | 出撃ゲート | 公開チャネル別の運用手順（社内投稿用文言テンプレート等） |
| `retrospective/` | 航海日誌 | 月次振り返り |
| `playbook/` | 運用マニュアル室 | チェックリスト・手順書（Arc召喚手順書等） |
| `drafts-internal/` | 資料庫 | 社内向け資料ドラフト |
| `private/` | 機密保管庫 | 最秘匿情報（昇進フィードバック記録・本音メモ等） |
| `tools/` | （後から追加） | 実際に開発したローカルAIエージェント等のツール置き場 |

安全対策として、公開リポジトリの `.gitignore` に `*bridge*` `*-strategy*` `planning/` 等のパターンを二重防御として仕込んでおり、万一 bridge のファイルが公開側に混入してもコミット対象から弾かれるようにしている。

## 3. 確立されたルール・執筆規約

01.txt の途中（絵文字を使わないでほしいという指摘以降）に確定し、03.txt冒頭のサマリでも正として維持されているルール群。

- **絵文字は一切使用しない**（強調したい場合はテキストベースの装飾を使う。表示環境によって見え方が変わることを嫌うため）
- **強調ラベル**: `[IMPORTANT]` `[NOTE]` `[WARNING]` などの英語角括弧ラベルを使用
- **ステータスラベル**: `[DONE]`（完了）`[WIP]`（進行中・レビュー/修正中）`[DRAFT]`（執筆中）`[PLAN]`（計画のみ）`[READY]`（公開予定日確定）`[LIVE]`（公開済み）`[-]`（該当なし）
- **重要事項の強調**: ハッシュ記号での枠囲み（例: `### [IMPORTANT] ... ###` の箱組み）
- **言語ポリシー**: マークダウン本文は日本語、コミットメッセージは英語（Conventional Commits形式）。これは意図的な運用で、コミットメッセージを英語学習の教材として使う個人的な狙いを兼ねている
- **英訳セクション**: 各マークダウンファイルの末尾に「English Translation」セクションを設置し、`[IN PREPARATION]` → `[IN PROGRESS]` → `[PARTIAL]` → `[COMPLETED]` のステータスとセクション別チェックリストで進捗を可視化する。翻訳は個人の英語学習を兼ねた気長な取り組みと位置付け、未完了でも本文（日本語）は完全に機能する設計とする
- **4点バッククォート**: マークダウン内にコードブロックをネストさせる場合、外側は4つのバッククォート（\`\`\`\`）で囲む（3点だと内側のコードブロックとぶつかって崩れるため）
- **罫線文字は許可**: 構成図等の図表には罫線文字（─│┌┐└┘├┤┬┴┼▶◀▼▲）の使用は問題ない。ただし半角記号だけで組む素朴なAA（`+--|` 等）は全角・半角混在で環境依存の崩れが起きやすいため非推奨とされ、崩れにくいMarkdownテーブルへの置き換えが基本方針
- **最小差分（minimal diff）の原則**: ファイルを修正する際は、ユーザーが貼った現状のファイルを正とし、依頼された変更に関係する行だけを書き換える。インデント・空行・整列など無関係な箇所は一切触らない（Gitの差分を最小に保つため。途中でこの原則が崩れて手戻りが発生した経緯があり、以降のルールとして明文化された）
- **コミット規約**: Conventional Commits（`<type>(<scope>): <subject>`）。type は feat/fix/docs/chore/refactor/style/revert。scope は ep01〜ep12、s2-ep01〜（シーズン2）、roadmap、readme、zenn、template、assets、i18n 等。1コミット=1つの論理的変更が原則（ただし初期構築等はまとめてOK）
- **タグ命名規則（独自、SemVerではない）**: `v<season>.0-init`（シーズン開始）、`v<season>.0-ep<NN>`（各話公開）、`v<season>.0-ep<NN>-fix<N>`（修正版）、`v<season>.0-final`（シーズン完結）
- **CHANGELOG**: Keep a Changelog形式のカテゴリ（Added/Changed/Deprecated/Removed/Fixed/Security）を採用し、コミット type と対応付ける

## 4. 技術的な決定事項・構成

### 想定読者向けのPCスペック分類
- **クラスA（軽量）**: VRAM 6-8GB / RAM 16GB
- **クラスB（標準）**: VRAM 12-16GB / RAM 32-64GB
- **クラスC（ハイエンド）**: VRAM 24GB以上 / RAM 64GB以上

### 実際の開発環境
ユーザーの実機は Intel Arc A770（VRAM 16GB）、Core i7-10700K、RAM 64GB、Windows 11。Intel Arc は素の Ollama では GPU アクセラレーションが効かないため、IPEX-LLM 提供の「Ollama Portable Zip」（依存関係同梱、環境構築不要）方式で召喚した。ドライバ確認・`ONEAPI_DEVICE_SELECTOR` によるGPU強制指定などのトラブル対応込みの手順書を bridge 側 (`playbook/summon-ollama-arc.md`) に保管している。使用モデルは DeepSeek-R1（1.5B/7B/14B/32B）、DeepSeek-Coder-V2 16B、Qwen2.5-Coder（14B/32B Q3）など。

### 開発方針：Claude Code等のクラウドAIをこのプロジェクトでは使わない
01.txt中盤で、会社が全社ではなく特定プロジェクト用に導入していた監視ツール（Agent Security Toolkit）が `.claude/settings.local.json` に社内プロキシ設定を自動注入することが判明した。個人プロジェクト、特に bridge の機密戦略情報がこのプロキシ経由で会社側の監査対象になりうるというリスクを検討した結果、`.claude/` を削除・`.gitignore` に追加し、「このプロジェクトではClaude Code等のクラウドAIエージェントを使わず、自作LLMの実験場とする」という開発方針が確立した。これは同時に「ローカルAI活用を説く連載自身がローカルAIだけで運営されている」というブランディング上の言行一致にもなっている（このチャット自体はブラウザ上でのAIとの壁打ちであり、リポジトリへの直接アクセス権は渡していない）。

### 自作ローカルコーディングエージェント「arc-agent.py」
連載のネタとは別軸で、ユーザーは実際に「Claude Codeのローカル版」に相当する自律型CLIエージェントを自作した（`run_deepseek.py` から `+7` まで世代を重ねて開発）。最終的に bridge 側 `tools/arc-agent.py`（非公開、将来的に整備して第5話「APIで叩く・自作スクリプト」のサンプルコードとして公開昇華する構想）として管理されている。主な機能・設計は以下の通り。

- ローカルOllamaサーバーとHTTP APIで通信し、複数モデルから選択可能なメニューUI
- `safe`（参照系は自動実行・変更系は要承認）/ `strict`（全操作要承認）/ `full`（全自動）の3実行モード
- モデル出力から `[EXECUTE_COMMAND]` と `[EDIT_FILE]`（あいまいマッチ対応のSEARCH/REPLACE）タグを解析して実行する、1ターン1アクションのReAct的ループ
- このループの振る舞いは `prompt.txt`（システムプロンプト）で厳密に定義されており、これ自体もバージョン管理された重要な成果物として扱われている（日本語での応答・英語での内部思考、1返答1アクションの厳守、マークダウンの説明だけで終わらせない、実在しない行を想像でSEARCHに書かない、等の作り込まれたルール群）
- 点字スピナーによる思考中表示、アイドル時のVRAM自動解放、起動時の残存プロセス自動掃除、作業ディレクトリ固定によるcd引き継ぎ問題の解決、同一アクション連続時の暴走防止
- `run_edit()` 内の未定義変数によるNameErrorバグを修正したものを「第8世代」としてコミット

### モジュール分割（リファクタリング、03.txt終盤で進行中）
肥大化した単一ファイルの arc-agent.py を `tools/agent/` パッケージ（`arc-agent.py` 本体 + `agent/scripts/` 配下のモジュール群）に分割する作業が進行中。分割順序は config.py（完了）→ ollama.py（作業中でチャット終了）→ ui.py → actions.py → tools_io.py → 本体を薄い司令塔にする、という依存の浅い順。1モジュールずつ「切り出し→動作確認→コミット」を繰り返す段階的方針で合意している。import方式は、分割フェーズでは明示列挙（`from scripts.config import X, Y`）で統一し、`import *` は PEP 8違反・名前衝突・意図不明瞭化のリスクから明確に却下。分割が完全に終わって安定してから、別フェーズでモジュール単位インポート（`config.MODELS` 形式）へ一括変換する方針で合意している。

### 将来構想：マルチエージェント・GPUバトンタッチ
ユーザーが自発的に発案し、良い設計として合意された将来構想。VRAM 16GBには大型モデルを2体同時ロードできないため、「解釈役（DeepSeek-R1、抽象指示を具体的な作業計画に分解）」→ VRAM解放・バトンタッチ →「作業役（Qwen2.5-Coder、計画を実行）」という逐次GPU占有のマルチエージェント・オーケストレーションを実装する構想。シーズン2連載の目玉コンテンツとして位置づけられている。

### 環境スペック検出スクリプト
読者が自分のPCのクラス（A/B/C）を判定するためのマルチOS対応スペック出力スクリプト（`check_spec.py`）も bridge/tools に作成済み。将来的に Public 側 `LLM-homelab/scripts/` へ昇華させる想定だが、未実施。
