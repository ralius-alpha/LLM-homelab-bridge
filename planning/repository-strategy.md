# リポジトリ運用方針

作成: 2026-08-23

エージェント実装がブリッジ内で肥大化したのを機に決めた、リポジトリの分け方と
公開方針のメモ。今後リポジトリを増やす時はこの方針に沿って判断する。

---

## 決めたこと（要約）

| リポジトリ | 公開 | 役割 |
|-----------|------|------|
| `LLM-homelab-bridge` | 公開 | **作戦室**。構想・方針・検証記録・各リポジトリへの入口 |
| `LLM-homelab` | 公開 | **記事にできる基礎レベル**のエージェント／API |
| `llm-homelab-agent` | **非公開** | 実際に自分で使う、高度にカスタマイズした実装 |

- 非公開リポジトリのコミットメッセージは**日本語**で書く（個人開発室のため）
- 機能ごとにリポジトリを分けてよい。**Gitの履歴は無理にきれいにしない**
- いいものができたら公開リポジトリ側に出し、記事で紹介する

## なぜこの形にしたか

### ブリッジを作戦室にする

ブリッジには `planning/` `playbook/` `crossings/` が既にあり、中身は元から
作戦室だった。そこにエージェント実装だけが同居していて、**36ファイル中26が
エージェント**という状態になっていた。実装だけ切り出せば、ブリッジは本来の
姿に戻る。

構想を置くリポジトリと実装を置くリポジトリを分ける利点:

- 作戦室は**履歴が読み物として残る**（実装のコミットに埋もれない）
- 実装側は**CI・タグ・リリースを自由に切れる**（ドキュメント更新でCIが回らない）
- 実装が複数になっても、作戦室が**ハブとして機能し続ける**

### 公開用と非公開用を分ける

分ける主な理由は「**履歴は永久に残る**」こと。一度公開すると過去のコミットが
すべて公開される。切り出し時点で追跡ファイルに個人情報・環境依存パスが
無いことは確認済みだが、今後カスタマイズを進めるほど混ざる可能性は上がる。

用途も違う:

- 公開側は「記事にできる」ことが要件。**分かりやすさ**を優先し、機能は基礎に絞る
- 非公開側は自分が使うためのもの。**動くこと**を優先し、履歴も整えない

## 環境固有設定の切り出し（公開の前提条件）

公開する以上、他の環境でも動かせる必要がある。**スペックによって変わる値を
1箇所に集約**した（`scripts/config.py` の「環境依存」節）。

| 値 | 集約前 | 集約後 |
|----|--------|--------|
| モデル名 | `roles/*/role.json` 7ファイルに直書き | `MODELS_BY_PURPOSE`（用途名で参照） |
| コンテキスト長 | 3箇所に直書き（8192 / 16384） | `NUM_CTX` |
| スキル結果の上限 | `chat_agent.py` | `MAX_SKILL_FEEDBACK` |
| ホスト・keep_alive | 既に config.py | そのまま |

`role.json` の `"model"` には用途名（`chat` / `coder`）を書き、
`role_loader.resolve_model()` が実体に解決する。実モデル名を直接書いても
動く（後方互換）ので、特定の役だけ別モデルにすることもできる。

GPUを載せ替えた・別のPCに持っていく、といった時に**触るのは config.py の
前半だけ**で済むようにしてある。

## 今後の設計方針

### 2つの実行モード

将来API経由で呼び出す際、次の2モードを想定している:

1. **サーバー操作モード** — リモート機はほぼ何もせず、サーバー側PCの操作権限を
   使って動く。リモート側の負担ゼロ、動作が速い
2. **リモート操作モード** — 自然言語処理はサーバー、操作権限はリモート側。
   リモート機での開発・作業を手伝う

**この2つは「2つのアプリ」ではない。** 役・プロンプト・スキル・安全網はすべて
共通で、違うのは**実行先だけ**。したがって分けるべき軸はアプリではなく
**executor（実行の担い手）**。リポジトリを2つに割ると、スキルを1つ足すたびに
両方を触ることになり、バージョンずれとクロスリポジトリのデバッグを抱える。

想定する構造:

```
llm-homelab-agent/
├─ agent/
│   ├─ roles/            役の定義
│   ├─ core/             dispatch・memory・role_loader・tools
│   ├─ skills/           検索・取得・要約・計算
│   └─ executors/        ★2モードの差はここだけ
│       ├─ local.py        サーバー上で実行
│       └─ remote.py       リモートの実行エージェントへ委譲
├─ apps/
│   ├─ cli.py            対話起動（現 chat_agent.py）
│   └─ api.py            API入口
└─ remote-executor/      リモート機に入れる小さな実行体
```

将来3つに分けるなら、その1つは `remote-executor` が適切。別マシンに
インストールする（配布単位が違う）、**操作権限を持つので小さく監査しやすく
保ちたい**、という実際の理由がある。ただし安定するまではサブディレクトリで
始める。**分けるのは後からできるが、統合は難しい。**

### API化の前に決めるべきこと（未着手）

現在の承認フローは**ローカルコンソール前提**で、両モードとも成立しない。

```python
raw = input("この 不可逆(変更/編集系) 編集を実行しますか？ (y/n): ")
```

- APIサーバーは `input()` でブロックできない
- 「誰が承認するのか」が未定義（リモートの人／サーバーの前の人）
- `exec_mode="full"` をネットワーク越しに使うと、**LLMによる遠隔コード実行**になる

承認は**非同期プロトコル**（サーバーが要求 → クライアントが応答）にする必要が
あり、`WORK_DIR` の制限もプロンプトではなく **executor 側で強制**すべき。
APIを作ってから直すのは難しいので、実装前に設計する。
